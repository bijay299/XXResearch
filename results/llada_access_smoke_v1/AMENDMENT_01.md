## Correction 2 — the memory arithmetic was wrong

**Claim corrected.** The asset matrix and report stated:

> "8 B × (4 bytes master + 4 + 4 Adam moments) ≈ **128 GB** of optimizer/master state alone"

**That arithmetic is incorrect.** The three arrays listed total **12 bytes/parameter**, which at
8.024 B parameters is **≈96 GB** (decimal) / ≈90 GiB — not 128 GB.

**Where 128 GB legitimately comes from.** A conventional **four-array** FP32 accounting —
parameters, gradients, and two AdamW moments, 16 bytes/parameter — gives **≈128 GB** (decimal) /
≈120 GiB at eight billion parameters. The original figure was right for a four-array accounting
but was paired with a three-array itemization.

| Accounting | Bytes/param | At 8,023,969,792 params |
|---|---|---|
| 3 arrays: FP32 master + 2 FP32 moments | 12 | **96.3 GB** (89.7 GiB) |
| 4 arrays: FP32 params + grads + 2 FP32 moments | 16 | **128.4 GB** (119.6 GiB) |

**Two further caveats the original omitted:**

- **FP32 master weights and FP32 optimizer moments are not automatic in every BF16 AdamW
  configuration.** Implementations differ: moments may be held in BF16, master weights may be
  absent (pure-BF16 training), or kept in FP32 only under specific mixed-precision wrappers.
  The original text implied a single inevitable layout.
- **Actual memory depends on more than optimizer state**: parameter and state precision,
  gradient storage and accumulation dtype, activations and checkpointing, MDU's additional
  **frozen anchor model** copy, and any sharding (FSDP/ZeRO) or CPU offload — each of which can
  move the real requirement substantially in either direction.

**The defensible conclusion is retained, and narrowed:** this small LoRA smoke test (0.1045% of
parameters trainable) **does not establish full-parameter MDU feasibility** on this hardware.
What the original over-claimed was precision, not direction — a rough order-of-magnitude
calculation cannot establish exact multi-GPU feasibility or infeasibility, and the amended text
no longer asserts that it does.

**Unchanged:** the *measured* figures — inference peak **15.004 GiB** and LoRA peak
**17.066 GiB** — are observations from `torch.cuda.max_memory_allocated()` and are untouched by
this correction.

## Correction 3 — asset and readiness claims narrowed to what was inspected

The original used universal absence phrasing ("does not exist publicly", "no author-matched
checkpoint exists", "no native LLaDA RWKU baseline exists"). The audit inspected two pinned
repositories and a recorded HF search; it cannot license universal non-existence claims. Replaced
with:

| Original wording | Amended wording |
|---|---|
| "No author-matched LLaDA TOFU checkpoint **exists**" / "does not exist publicly" | "**No author-matched TOFU checkpoint was located in the inspected release and recorded search.**" |
| "**No native LLaDA RWKU baseline exists**" | "**The pinned MDU release contains no LLaDA RWKU preset/evaluator; its released RWKU path is Dream-specific.**" |
| "`dllm` … upstream identified by symbol match only" | "**The exact `dllm` dependency revision used by MDU remains unverified.**" |

**The real reproduction limitations are retained in full**, because they are what the inspected
sources do support: MDU's TOFU SFT code is **unavailable** in the pinned release (its README says
so explicitly), the author-matched starting checkpoint is **unresolved**, and the `dllm`
dependency **pin is unverified**. Narrowing the epistemic claim does not soften the practical
blocker.

### Three further factual corrections

1. **TOFU corpus size — corrected.** The original described "the 200-row TOFU corpus". **TOFU
   comprises 200 fictional authors × 20 question–answer pairs = 4,000 pairs.** Verified against
   the HF datasets-server (`evidence/tofu_row_counts.json`): `full` = **4,000** rows,
   `forget10` = 400 (10%), `retain90` = 3,600, `real_authors` = 100, `world_facts` = 117. The
   erroneous "200" most likely came from `forget05`, which is 200 rows. This makes the
   unreleased 1000-epoch SFT stage a **larger** undertaking than the original implied.
2. **Missing license metadata — conclusion softened.** The original stated the two unlicensed
   third-party SFT checkpoints had "**no license** … which **blocks redistribution**". That is an
   unsupported categorical legal conclusion. Corrected to: **absent declared license metadata
   means permission and provenance remain unresolved**, which is a reason to seek clarification
   before use or redistribution — not a determination of law.
3. **Shard count — not evidence of incompatibility.** The original flagged that the third-party
   checkpoints ship 4 safetensors shards where the official model ships 6, calling it an
   "unexplained divergence". Corrected to state plainly: **a 4-vs-6 shard count alone does not
   establish model incompatibility** — shard layout is a packaging choice independent of
   architecture or dtype. It remains an unverified detail, not a defect.

### RWKU framing corrected

The original §9 recommended the LLaDA RWKU adaptation as *the* next step. Amended to present it
as **one possible future experimental route among others, not the only route, and not an
already-qualified baseline**. Added as a precondition that the original omitted:

> **Pristine LLaDA must first demonstrate recall of the selected target facts.** An unlearning
> experiment can only measure forgetting of knowledge the model demonstrably holds; without a
> positive recall baseline on the chosen entities, a low post-unlearning score is
> indistinguishable from the model never having encoded the facts.

**No adaptation work has been started.** The separate cloud method team will inform the next
experimental choice.

**Enforcement wording corrected.** The distinction now stated consistently:

- **Enforced:** per-job wall-clock timeouts (1800 s, coreutils `timeout`, SIGTERM then SIGKILL
  after a 30 s grace). A single job could not exceed its ceiling. The cumulative GPU counter
  charged every attempt including failures.
- **Advisory only — not enforced:** the aggregate elapsed-time, aggregate GPU-hour, CPU-core-hour
  and storage limits. These were **not scheduler or cgroup quotas**. They were computed and
  checked between phases; nothing would have terminated the session had an aggregate been
  crossed mid-phase. Every budget finished far under cap, so the distinction was never
  load-bearing in this run — but it must not be described as a hard cap.

**No accounting discrepancy was found.** The recovered logs corroborate the GPU-second and
CPU-core-second figures exactly, so the original numbers are retained with the qualifications
above rather than revised.
