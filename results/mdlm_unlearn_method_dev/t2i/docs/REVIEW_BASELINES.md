## 1. THE RELOAD GUARD — **DEFECT FOUND** (guaranteed false negative in smoke mode)

### What verifies

* Same revision **and** variant as the trainer. `ARGS` carries `--variant "$PIN_VARIANT"`
  (`run_r2_meta_official.sh:277`); stage 9 is invoked with the same shell variable
  (`run_r2_meta_official.sh:525`). They are one variable and **cannot diverge**.
* Variant floor is actually computed: `other = base(None if variant else "fp16")`
  (`run_r2_meta_official.sh:539`), `f_var = floor(same, other)` (`:552`).
* Guard is `r_same <= 10 * f_var -> sys.exit(1)` (`:560-564`), and both the floor and the
  calibration delta are printed and written to `reload_check.json` (`:555-573`), so the comparison
  can be judged rather than trusted.
* Key-set, param-count and finiteness assertions precede it (`:540-543`).

### Independently replicated measurement

SD-1.4 UNet @ `133a221b8aa7292a167afc5127cb63fb5005638b`, fp32 load of both forms, on CPU:

| quantity | measured |
|---|---|
| tensors differing, `fp16` variant vs `main` | **686 / 686** |
| global relative Frobenius | **2.074001e-04** |
| `fp16variant == main.half()` bit-exact | **686 / 686** |
| `‖W‖` (fp16 variant and main alike) | 1201.527344 |
| params | 859,520,964 |

This matches the coordinator's figure exactly. The guard threshold is therefore
`10 x 2.074001e-04 = 2.074e-03`.

### Attempts to defeat it — the guard HOLDS against all three

* **Trainer's and guard's variant both wrong but equal.** The guard still measures against the
  initialisation the trainer was actually given, so the *no-op* question is answered correctly. What
  it cannot detect is the *scientific* deviation; that is separately recorded as TIER I-6
  (`:174-179`, `:394-396`). Worth stating plainly: upstream passes **no** `--variant` (default
  `None` → `main` fp32), so our "OFFICIAL" reproduction trains from a half-rounded init. Recorded,
  not a code bug.
* **Floor computation loading the wrong thing.** Stage 3 asserts `a.variant` is truthy
  (`:316`), so `variant` is never empty and `other` is always `main`. `f_var` is always the real
  2.074e-04 floor; the denominator is `‖same‖`, the correct init.
* **Variant mismatch in either direction.** A checkpoint that did not train would land at
  `r_same ≈ f_var`, i.e. 10x *below* the threshold → the guard fires. Fails in the **safe**
  direction. This is a genuine repair of the precedent defect.

### DEFECT: a genuinely-trained checkpoint FAILS the guard in `R2_MODE=smoke`

`esd_meta.py:867` uses `optim.AdamW`, whose per-parameter step saturates at ≈ `lr`. With
`lr = 1e-5` (TIER R, `:133`) and the default `META_SMOKE_STEPS=2` (`:476`), the **upper bound** on
the relative delta — every one of 859.5M parameters moving the full `lr` in a consistent direction,
which never happens — is

```
2 * 1e-5 * sqrt(859_520_964) / 1201.527 = 4.88e-04
```

That is **4.2x below** the 2.074e-03 threshold. Break-even at the saturating bound is ≈ 9 steps; a
2x margin needs ≈ 20, a comfortable one ≈ 30+.

Consequence: **stage 7's "MINIMAL REAL UPDATE" — the only mode whose stated purpose is to
distinguish "the script runs" from "the script trains" (`:472-475`) — cannot pass stage 9 at its own
default.** It will print `REFUSING TO CALL THIS TRAINED` and `die`. The guard is correct in
construction and mis-tuned against the mode it most needs to serve.

Full mode is unaffected: 1500 steps gives a bound of 3.66e-01, ~175x the threshold.

Fix direction (not applied — reporting only): raise `META_SMOKE_STEPS` to ≥30, or make the guard
mode-aware and state the expected-delta model (`steps * lr * sqrt(P) / ‖W‖`) next to the floor so
both bounds are visible.

any per-tensor phrasing of the rule-out is unsupported and should not be used.

### CAVEAT 8b — benign explanations: I looked for a missed one and found none outside H-A/H-B

Candidates I tested or traced: a different base **revision** of `CompVis/stable-diffusion-v1-4`; a
CompVis `sd-v1-4.ckpt` → diffusers conversion run with `--extract_ema`; `sd-v1-4-full-ema.ckpt`.
All three are instances of the stated **H-B** ("cross-attention-only but from a different SD-1.4
instantiation, EMA vs non-EMA being the leading candidate"), so they are covered rather than missed.
A safetensors/pickle conversion and a pruned/re-keyed dict are genuinely ruled out above (both are
value-preserving or key-changing, and neither signature is present). A mislabelled full-UNet
(ESD-u) checkpoint despite `ESDx1` is the stated **H-A**. I found **no surviving benign cause
outside H-A and H-B**.

One honest limit, consistent with the write-up: the local cache holds **exactly one** SD-1.4
snapshot (`133a221b…`) and the host is offline, so no alternative-revision test is performable here.
H-B is untestable on this machine, as claimed.

## 9. FAIL-CLEARLY — **DEFECTS FOUND**

### 9a — R2 cpu mode reports "stages 1-4 passed" having skipped stage 4

See **3a** and **3b**. `R2_MODE=cpu` exits 0 with
`R2 CPU VERIFICATION COMPLETE ... stages 1-4 passed` whenever the pool root is absent — which is the
case for an invalid scheme *and* for the recommended `coherent` scheme. The success message asserts
more than was executed. This is the review brief's stated failure mode.

### 9b — `run_r1c_eval.sh` reuses stale artifacts and still reports DONE

Every expensive step is gated on output existence:

```
:92   if [ ! -f "adapters/$C/unet.pt" ]        -> compose control
:97   if [ ! -f "outputs/gen_$C.json" ]        -> evaluate control
:103  if [ ! -f "adapters/$A_TAG/unet.pt" ]    -> compose IMMA arm
:139  if [ ! -f "outputs/gen_$A_TAG.json" ]    -> evaluate IMMA arm
```

This is **structurally the same defect as the blank-image filter being repaired**
(`if [ ! -f metadata.csv ]`): an existing, stale, or partially-written artifact is silently reused,
the strict composer never runs, and the script still prints `R1c DONE`. Nothing checks a composer
version or an input sha256.

It is live today. `adapters/REF_imma_vangogh/unet.pt` exists and was produced by the **pre-audit
fuzzy** composer — `scripts/r1_eval_imma.py:16-19` says so itself, and `logs/r1c_eval.log` confirms
it with the old print string `[r1eval] composed base+ESD+IMMA: overlaid 160/160 IMMA tensors`, which
no longer appears anywhere in the current file. That adapter also carries **no** `QUARANTINE.md`
(the unconditional `cat >` at `:108-138` only writes one for arms this script composes).
`adapters/ESD_vangogh_official/` does not exist, so the mandatory control has never been built.

### 9c — the label-collapse detector does not fire on the canonical case it was written for

`run_r1c_eval.sh:157`: `if zeros >= 0.6 * len(ap) and am['target_suppression_acc'] > 0.5`.
With 12 concepts the threshold is **7.2**. Measured from `outputs/gen_REF_imma_vangogh.json` —
the exact artifact the header cites at `:31-32`:

```
target_suppression_acc = 0.8667   legacy_retain8 = 0.0333
exact zeros = 7 of 12  (church, garbage_truck, english_springer, french_horn, gas_pump,
                        golf_ball, monet)
7 >= 7.2  ->  False  ->  LABEL-COLLAPSE SIGNATURE never prints
```

Two problems in one: the threshold is on the wrong side of the motivating case, **and** the header
says *"eight non-targets at exactly 0.000"* when the true count is **seven** — the mis-stated
number is precisely what makes 0.6 look like a safe threshold. The warning that exists to stop a
label collapse being read as a result is inert on the only example of it we hold.

### 9d — stated intent not achieved: smoke-mode validation sampling still runs

`run_r2_meta_official.sh:482` sets `--eval_every $((SM_STEPS + 1))` with the comment
`# skip validation sampling`. But `esd_meta.py:1070` is

Not a correctness defect, but the comment asserts something the code does not do, and it adds

## WHAT I WOULD BLOCK THE GATE ON

1. **The smoke-mode false negative (item 1).** `R2_MODE=smoke` cannot pass stage 9 at
   `META_SMOKE_STEPS=2`: the saturating-AdamW upper bound is 4.88e-04 against a 2.074e-03
   threshold. Until the step count is raised (≥30) or the guard is made mode-aware, **"the script
   trains" is unprovable** — which is the one thing the smoke mode exists to prove. The guard's
   construction is correct; only its tuning is wrong.
2. **R2 cpu mode claiming "stages 1-4 passed" when stage 4 was skipped (3a, 3b, 9a).** Validate
   `META_POOL_SCHEME` in the launcher against the builder's `choices`, and make the terminal message
   name what actually ran. As it stands a bare `coherent` CPU run reports success with
   `"pools": null`.
3. **`run_r1c_eval.sh`'s output-existence gates (9b).** Same defect class as the bug being
   repaired, and already live: the pre-audit fuzzy `adapters/REF_imma_vangogh/unet.pt` is on disk,
   unquarantined, and would be reused. Key the gates to a recorded composer version plus input
   sha256, or drop them.
4. **The label-collapse detector (9c).** Fix the threshold so it fires on 7/12, and correct
   "eight" → "seven" in the header.
5. **Pool fingerprints (3c).** The byte-provenance guarantee is inert for the only pools that
   exist. Either record fingerprints for the legacy pools or stop claiming the capability.

Not blocking, but fix before publication: the `--max` drift gap (6a), the unasserted dataset-ordering
assumption behind `selected_files` (6b), the per-tensor phrasing of the ESD floor rule-out (8a), the
missing gamma2-triplicate drift guard (5b), and TIER R's omission of upstream's own disclaimer (5a).

## WHICH CLAIMS NEED A REAL BOUNDED GPU RUN

Everything above was settled on CPU **except** these, which cannot be:

* **R2 stage 7 → 9 → 10 end to end.** Does `--devices "0 0"` with `finetuning_method=full`,
  `train_batch_size=10`, `resolution=512` fit a 40 GB card when upstream's README cites 80 GB A100s
  and both teacher and student are co-resident? And what is the **actual** rel delta at whatever
  smoke step count is chosen — the AdamW bound above is an upper bound, so the real margin over
  2.074e-03 must be measured, not predicted.
* **R2 stage 4 for `coherent`.** The pools need a GPU to build and have never existed, so their
  content validation, per-prompt proportions, fingerprints and claim scope are entirely untested.
  This is the scheme any concept-erasure claim would rest on.
* **R1 stage 4 smoke** — the 160-tensor / 93,536,640-param scope assertion has only been read, never
  executed.
* **R1b `s20`** — the README-faithful 1000-step / 500-ascent-update artifact does not exist yet; the
  5.00x ratio is proven arithmetically and from the log, but the faithful counterpart is unbuilt.
* **R1c's ESD-only control** (`adapters/ESD_vangogh_official`) — absent. Without it the IMMA
  standalone numbers have nothing to be compared against, which is the stated reason the control is
  mandatory.
* Not GPU, but **network**: H-B (EMA vs non-EMA) needs the non-EMA weights, which are not cached.
